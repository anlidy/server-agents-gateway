# v2：个人服务器 Hub

- **Version:** 2.1.3
- **Status:** 已实现（2.1.0：去掉沙箱 + agent 协作，见 §10；2.1.1：会话过期重拉工具 + 返回瘦身，见 §11；2.1.2：rm 包装器修复 + 会话兼容，见 §12；2.1.3：token 脱敏不再误伤 `sag_` 开头的名字，见 §13）
- **相对:** v1.0.0（零信任白名单控制面）
- **本文替代:** 不存在更早的 v2 草稿；实现以本文为准
- **修订:** 共享记忆改为单一文档，不上资产表

v1 把网关写成「生产控制面」：命令白名单、fencing token、资产按 RUNNING/STOPPED 对账。个人 Linux 服务器上通常只有同一个人的几个 Agent，要的是记下每次操作、有一份共享画像、误删能还原。

v2 换轴，不换协议：MCP over SSE、per-agent Bearer、SQLite、零第三方依赖。改执行器、审计、删除路径；**世界画像就是一篇 markdown，不是 CMDB。**

## 1. 四层

| 层 | 职责 |
| :--- | :--- |
| 身份 | per-agent token。决定审计里的 `agent_id`，以及谁能签发凭据。 |
| 共享记忆 | 一篇 `SERVER_AGENTS.md`。库存人写，状态机写。 |
| 痕迹 | 每次工具调用都入库，可完整回放。 |
| 手 | 默认全开的 `bash -lc`；MCP 读/写/删。删除进回收站。 |

防出事靠完整日志和回收站，不靠拦截命令。

**自保（不是权限模型）：** `hub_write_file` / `hub_delete_file` / `rm` 包装器拒绝改动数据库文件、`.env`、`data/`。`/bin/rm` 仍可真删。

**不设沙箱（2.1 起）：** systemd 单元以 root 运行，去掉了 `ProtectSystem`、`ProtectHome`、`PrivateTmp`。`hub_shell` 就是宿主上的 root：能写 `/etc`、`/usr`、`/root`、改 systemd，`/tmp` 与 SSH 会话共享。代码里除了上面的自保，没有路径白名单/黑名单。代价是：token 泄露 = 服务器 root 泄露，只给可信 agent 签发。

**不做：** 持久 PTY、`LD_PRELOAD`、快照、allowlist 双模式、Postgres、多租户、资产表、fencing/claim。每次 `hub_shell` 是新进程。

## 2. 相对 v1

| v1 | v2 |
| :--- | :--- |
| 白名单 argv | `hub_shell`：`bash -lc` |
| 无读文件 | `hub_read_file` |
| `hub_edit_file` + `.bak` | `hub_write_file`，覆盖进回收站 |
| `hub_delete_file` 硬删 | 回收站，30 天，可 restore |
| `hub_manage_service` / 强制锁 | 删除；服务走 shell |

| `gateway_assets` + LLM 生成 overview | **一篇 md 为真源**；状态区自动刷，库存区手写 |
| 旧工具名别名 | 不留 |

保留：SSE/JSON-RPC、token 签发/吊销（仅 root admin）、WAL SQLite、密钥脱敏。

## 3. 工具

原则：shell 干活；MCP 只保留结构化读写、回收站、读画像、查审计、管身份。

| 工具 | 说明 |
| :--- | :--- |
| `hub_issue_agent_token` / `hub_revoke_agent_token` | 仅 root admin。在线签发一律 operator |
| `hub_shell` | `command` + `reason` 必填；可选 `cwd`、`timeout_seconds` |
| `hub_read_file` | `path`；可选 `offset`/`limit` |
| `hub_list_dir` | 非递归列目录 |
| `hub_mkdir` | `path` + `reason`，mkdir -p |
| `hub_write_file` | `path` + `content` + `reason`。已存在则先回收 |
| `hub_patch_file` | `old_string` → `new_string`；默认必须唯一，`replace_all` 才全改；先进回收站 |
| `hub_delete_file` | 进回收站 |
| `hub_list_trash` / `hub_restore_file` | restore 按 `trash_id`；目标已存在则失败 |
| `hub_get_overview` | 读 `SERVER_AGENTS.md`（每次读盘，不缓存） |
| `hub_rebuild_overview` | 立刻重刷状态区，不改库存区 |
| `hub_query_audit_logs` | 只返回事件行 |
| `hub_get_audit_event` | 按 id 取事件 + body |
| `hub_get_status` | 主机 vitals（负载/内存/磁盘/失败单元）+ 库存探活的 JSON；不含 runbook |

删除：`hub_execute_command`、`hub_edit_file`、`hub_register_asset`、`hub_query_assets`、`hub_upsert_asset`、`hub_manage_service`、`hub_acquire_lock`、`hub_renew_lock`、`hub_release_lock`、`hub_cleanup_temp`、`hub_claim`、`hub_release_claim`。

改机器或改文档的工具 `reason` 必填。所有 `tools/call` 不论成败都写审计。查询类不把结果全文再写入 body。

## 4. 执行

```python
subprocess.run(
    ["/bin/bash", "-lc", command],
    cwd=cwd, env=env, capture_output=True, text=True, timeout=timeout,
    start_new_session=True,
)
```

- 默认 cwd：`GATEWAY_SHELL_CWD`，否则 `$HOME`，否则 `/`。
- 默认超时 120s，上限 3600s。超时 `killpg`，`exit_code=-1`，已有输出仍入库。
- 不改 `PATH`，不接受客户端 env。
- `rm` 绑成最外层 shell 里的 bash 函数，调用 `wrappers/rm` 的绝对路径（login shell 改 PATH 也丢不掉）。**不导出**（2.1.2 起），子进程拿到的是真 rm，见 §12。操作数只解析父目录、不跟随最后一级软链接，和 GNU rm 一样。不包装 `mv`。
- stdout+stderr 合计 2MB，响应与入库同一份（脱敏后）。
- `finally`：探活并只改文档的状态区（见 §6）。

## 5. 审计

拆表，全文仍在 SQLite。列表不 `SELECT` 正文。

```sql
CREATE TABLE audit_events (
    id TEXT PRIMARY KEY,
    timestamp TEXT NOT NULL,
    agent_id TEXT NOT NULL,
    tool_name TEXT NOT NULL,
    action_type TEXT NOT NULL,
    target TEXT NOT NULL,
    reason TEXT NOT NULL DEFAULT '',
    status TEXT NOT NULL,           -- SUCCESS | FAILED | REJECTED
    exit_code INTEGER,
    cwd TEXT,
    duration_ms INTEGER,
    params_json TEXT,
    trash_id TEXT,
    output_bytes INTEGER NOT NULL DEFAULT 0,
    truncated INTEGER NOT NULL DEFAULT 0,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE audit_bodies (
    event_id TEXT PRIMARY KEY REFERENCES audit_events(id) ON DELETE CASCADE,
    stdout TEXT,
    stderr TEXT,
    diff TEXT
);
```

`SUCCESS` / `FAILED` / `REJECTED` 含义同前。签发 token 明文不入库。`diff` 上限 64KB。审计不自动删。

v1 `gateway_audit_logs` 迁完改名为 `gateway_audit_logs_v1`。

## 6. 文档 = 共享记忆

不维护资产表。路径：`<gateway_root>/SERVER_AGENTS.md`。

「实时」拆成两件事，混在一起就会又脏又假：

| | 状态（活着吗） | 库存（有什么、怎么动） |
| :--- | :--- | :--- |
| 谁写 | 网关自动刷 | Agent / 人用 `hub_write_file` |
| 多久 | 对账周期 + 每次 shell/写删之后 | 拓扑变了再改（新服务、搬家、下线） |
| 不做什么 | 不写进库存段落 | 不写「当前 RUNNING」——那会过期 |

文档固定四个一级标题，顺序不变。缺了启动时补骨架，不删人写的其它一级标题（附录可以有，对账器不碰）。

```markdown
# <hostname>

<!-- sag-status:start -->
> probed_at: 2026-09-13T22:00:00+0800

| id | probe | state |
| caddy | systemd caddy.service | up |
| app | docker app | down |

Untracked:
- docker:something-new
<!-- sag-status:end -->

## Host

这台机器是干什么的（一两段）。稳定事实：公网入口、SSH 端口、备份落哪、磁盘角色。
**不要**写 load、内存百分比、某服务当前 up——那是 `hub_get_status` 和上面状态区的事。

## Inventory

### caddy
- probe: systemd caddy.service
- path: /etc/caddy/Caddyfile
- url: https://example.com
- listen: 0.0.0.0:443
- depends: docker:app

反代。改 Caddyfile 后 `systemctl reload caddy`。证书由它自己管。

### app
- probe: docker app
- path: /opt/app
- depends: caddy

compose 在 `/opt/app`。改完 `docker compose up -d`。

## Conventions

给 Agent 的规矩：改拓扑要改 Inventory；密钥只写路径不写值；大改先看审计。可空。
```

| 区 | 谁写 | 内容 |
| :--- | :--- | :--- |
| `#` 标题 | 人，一次 | 主机名或 hub 名 |
| `sag-status` | **只许网关** | 探活表 + Untracked |
| `## Host` | 人/Agent | 这台机的稳定身份 |
| `## Inventory` | 人/Agent | 一节一个东西 |
| `## Conventions` | 人/Agent | 协作约定，可空 |

`hub_write_file` 若带了整文件：网关抽出库存/Host/Conventions 保存，再重刷状态区，避免把围栏盖掉。

### 6.2 库存小节

`## Inventory` 下每个 `### <id>` 是一条。`<id>` 用短名（`caddy`、`app`），状态表用同一个 id。

小节开头的列表是给对账器看的，一行一个，可重复、可缺：

```
- probe: systemd <unit>      # 可省略 .service
- probe: docker <container>
- probe: http <url>
- probe: tcp <host:port>
- path: <绝对路径>
- url: <公网或内网 URL>
- listen: <addr:port>
- depends: <id>
```

正则：`^- (probe|path|url|listen|depends): (.+)$`。`probe` 的值再拆成 `^(systemd|docker|http|tcp) (.+)$`。

列表下面是自由 markdown（怎么重启、坑）。**禁止**在库存里写「当前 RUNNING / 昨天磁盘 40%」。

一个项目 = 一节 `path` 指向根目录，不要给每个源文件开节。

### 6.3 状态怎么同步

对账器：

1. 收集库存里所有 `probe` 行并探活（超时 3s；异常 → `unknown`）
2. `docker ps -a` 的容器名若不出现在 Inventory 正文里 → `Untracked`（只扫容器，**不**扫全部 enabled systemd，噪音太大）
3. 只替换 `sag-status` 围栏，不进回收站

触发：`RECONCILE_INTERVAL_SECONDS`、`hub_shell`/写删的 `finally`、`hub_rebuild_overview`。Agent 开工 `hub_get_overview` 读盘。不做文档推送。无进程内整篇缓存。

### 6.4 库存怎么不烂掉

- 禁止 LLM/对账器改 `## Inventory` / `## Host` / `## Conventions`
- 新增、下线、搬家、改入口 → 改对应 `###` 节
- Untracked 是漏网：补节或确认不管
- 两人同时写：后写覆盖，旧版在回收站
- 不根据命令文本自动插条目

v1 `gateway_assets` 仅在 md 不存在或 Inventory 为空时导出成 `###` 草稿，然后表改名为 `gateway_assets_v1`，不再用。

### 6.4.1 第一篇谁写

文件从无到有只发生一次，分三层，不靠 LLM 整篇生成：

1. **网关写骨架。** 启动时若 `SERVER_AGENTS.md` 不存在，按 §6.1 写出标题（hostname）、空状态围栏、空的 Host / Inventory / Conventions。对账器第一次跑就会填状态区。
2. **网关可选倒库存。** 若这是 v1 升级且 `gateway_assets` 里有行，把每条收成一个 `###` 小节（title、description、paths、endpoints → `path`/`url`/`listen`/`probe`）。只倒这一次。新装没有旧表就跳过，Inventory 保持空。
3. **Host 正文和「这台机到底是什么」：人，或第一个进来的 root admin Agent。** 网关不知道「这是个人 VPS、备份在哪」。Conventions 同样。之后谁改拓扑谁改对应小节。

`hub_rebuild_overview` 只重刷状态围栏，不写第一篇，也不请 LLM 编 Host/Inventory。

### 6.5 `hub_get_status`

给 Agent 的 **机器快照**，JSON，不读 runbook。和文档分工：文档回答「这是什么、怎么动」；本工具回答「现在堵不堵、盘满不满、点名的服务活不活」。

采集都有短超时（2–3s），单项失败就该项 `"unknown"`，不让整个调用挂死。

```json
{
  "timestamp": "2026-09-13T22:00:00+0800",
  "host": {
    "hostname": "box",
    "os": "Ubuntu 24.04",
    "kernel": "6.8.0-...",
    "arch": "aarch64",
    "uptime_seconds": 86400,
    "reboot_required": false
  },
  "cpu": {
    "cores": 4,
    "loadavg": [0.12, 0.20, 0.18]
  },
  "memory_mb": {
    "total": 11900,
    "used": 4100,
    "available": 7200
  },
  "swap_mb": {
    "total": 0,
    "used": 0
  },
  "disks": [
    {"mount": "/", "fstype": "ext4", "total": "50G", "used": "20G", "avail": "28G", "pct": "42%"}
  ],
  "systemd_failed": [],
  "docker": {
    "available": true,
    "running": 4,
    "total": 6
  },
  "probes": [
    {"id": "caddy", "probe": "systemd caddy.service", "state": "up"}
  ],
  "untracked": ["docker:something-new"]
}
```

| 字段 | 来源 | 为什么要 |
| :--- | :--- | :--- |
| `host` | `hostnamectl` / `/etc/os-release` / `uptime`；`reboot_required` 看 `/run/reboot-required` 是否存在 | 这是哪台、该不该避开重启 |
| `cpu.loadavg` + `cores` | `/proc/loadavg`、`os.cpu_count()` | 现在堵不堵 |
| `memory_mb` / `swap_mb` | `free -m` 或 `/proc/meminfo` | OOM 前兆 |
| `disks` | `df -hT -x tmpfs -x devtmpfs -x overlay -x squashfs` | 所有真实挂载，不只 `/` |
| `systemd_failed` | `systemctl --failed --plain --no-legend` | 有东西已经挂了 |
| `docker` | `docker ps -a` 计数；没装则 `available: false` | 容器粗看一眼 |
| `probes` / `untracked` | 与状态区同一次探活 | 不用解析 markdown |

**不要塞进 get_status：** 全进程表、`ss` 全监听、docker 逐容器状态、日志、温度、网卡流量、资产 wiki 正文。那些用 `hub_shell` 或 `hub_get_overview`。

`probes` 为空（库存还没写 probe）时仍返回主机 vitals，这样新装也能用。

### 6.6 谁维护、怎么维护

没有专职文档管理员，也没有 LLM 自动写库存。三条规则：

| 区 | 维护者 | 何时 |
| :--- | :--- | :--- |
| 状态围栏 | 网关进程 | 周期 / 每次动手之后，无需任何人记着 |
| 某个 `###` 小节 | **刚改了这个东西的那个 Agent**（人用同样工具也算） | 同一轮任务里改完拓扑就改文档，不是事后作业 |
| `## Host` / `## Conventions` | 人为主，Agent 可补 | 机器角色、入口、协作规矩变了 |

「谁改谁写」：你 `docker compose up` 了一个新项目，同一轮用 `hub_write_file` 加一节；你下线了某个容器，删掉或注明下线。别的 Agent 没有义务替你补，除非他们看见 Untracked。

Untracked 的处理也没有指定人：任何一个开工时 `hub_get_overview` / `hub_get_status` 看到了，要么补节，要么在 Conventions 写「故意不管 xxx」，要么这轮不管（下次还在）。不设 deadline，不自动删容器。

工具层怎么兜着：

- `hub_shell` / `hub_write_file` / `hub_delete_file` 的 description 写明：增减服务、改入口、搬家时要改 Inventory。
- `hub_get_overview` 每次读盘，Agent 开工先读。
- 网关不根据命令猜着插小节，也不定期让 LLM 重写文档。

人（或第一个 admin Agent）要做的：给 Host 写两段话。Inventory 在 v1 升级时网关会倒一版草稿，新装则等谁先上服务谁写小节。之后日常谁改谁写，人偶尔看 Untracked。

## 9. 实现

代码在 `sag/` 包内。根目录 `server.py` 只做入口。测试在 `tests/`。新建 `sag/trash.py`、`wrappers/rm`。资产表不进入 v2 schema。

## 10. 2.1：去掉沙箱、agent 协作

### 10.1 不设沙箱

systemd 单元不再带 `ProtectSystem` / `ProtectHome` / `PrivateTmp`。`hub_shell` 是宿主上真正的 root，`/tmp` 与 SSH 共享。代码里唯一的路径限制仍是 §1 的自保（`data/`、`.env`）。审计、回收站、脱敏不变。token 泄露 = root 泄露。

### 10.2 消息与任务

以前 agent 之间靠在服务器上写 md 互相留言。2.1 起用消息：

```sql
agent_messages(id, thread_id, reply_to, from_agent, to_agent, subject, body, task_id, created_at)
agent_message_recipients(message_id, agent_id, read_at)      -- 每个收件人一行
agent_groups(group_name, agent_id, added_by, added_at)
agent_tasks(id, title, description, status, created_by, assignee, result, thread_id,
            created_at, updated_at, closed_at)               -- status: open/claimed/done/cancelled
```

`init_db()` 用 `CREATE TABLE IF NOT EXISTS` 建表，老库启动即补齐，无需单独迁移。

- `from_agent` 只取自调用者 token；参数里带 `from` / `from_agent` / `sender` / `created_by` 直接报错。
- `to_agent` 存发件时的表达式（`agent_id`、`*`、`prefix:*`、`@group`，逗号分隔），发送时按当时 ACTIVE 的 agent 展开到收件人表。广播和组不含发件人自己。
- 只有发件人和收件人能读一条消息或一个线程。
- 未读提示：`tools/call` 成功时，若调用者有未读消息，在 `content` 末尾追加一个 text 项。选它而不是改第一项文本或加 `_meta`：第一项 JSON 保持可解析，模型又能看到。`hub_inbox` / `hub_read_message` / `hub_mark_read` 不追加。
- 任务的每次变化（认领、完成、取消……）在任务线程里给创建者和负责人（除操作者本人）发消息，于是任务进展也走同一个未读提示。
- 审计：`message_send` / `message_reply` / `group_set` / `task_*`。正文进 `audit_bodies.stdout`，经 `audit_redact` 脱敏；消息表存原文（交接可能需要原文），所以 `data/gateway.db` 应只让 root 可读（建议 `chmod 600`）。

## 11. 2.1.1：会话过期重拉工具、返回瘦身

### 11.1 重启后客户端自动拿到新工具

`/mcp` 仍不保存会话状态，也不开服务端推送流（GET 仍是 405），所以不走 `notifications/tools/list_changed`。
做法：进程启动时生成 `BOOT_ID`，`initialize` 的响应头带 `Mcp-Session-Id: <BOOT_ID>.<随机>`。之后的请求若带了别的 boot 发的会话 ID，回 404。
MCP 规范要求客户端收到 404 后重新 `initialize`，于是会重新 `tools/list`。工具只在发版重启时变化，所以这正好覆盖。
不带会话头的请求（`sag-call`、老客户端）照旧放行。

2026-09-28 用 Claude Code 2.1.283 实测：SAG 重启并新增工具后，客户端对旧会话的 `tools/call` 收到 404，自动重新 initialize、重试这次调用，并重拉工具列表；同一会话里的模型随即能看到并调用新工具，无需手动重连。

### 11.2 返回瘦身

- `hub_get_overview(section=)`：`toc` 返回状态表和标题列表；否则按逗号分隔的 `##` / `###` 标题（不区分大小写）返回对应小节。不传照旧返回全文。
- `hub_shell` 结果不再回显 `command`。
- `hub_query_audit_logs` 列表去掉 `created_at`（`timestamp` 的 UTC 副本）和空字段；`params_json` 解析成 `params`，只留不和列重复的键（比如 shell 命令超过 200 字、`target` 被截断时才带完整 `command`）。`hub_get_audit_event` 仍返回完整行。
- `hub_delete_file` 支持 `paths`：逐个进回收站、逐个审计，返回每个路径的结果；受保护路径标 `REJECTED`，不影响其余路径。

## 12. 2.1.2：rm 包装器修复、会话兼容、回收站清除

### 12.1 rm 只管命令行里直接写的那一个

2026-09-29 通过 hub_shell 跑 `apt-get dist-upgrade` 时，cloudflared 旧版 postrm 的 `rm -f /usr/local/bin/cloudflared`（指向 `/usr/bin/cloudflared` 的软链接）把刚解包的新二进制挪进了回收站，差点重启后隧道起不来。两个问题叠加：

1. `rm()` 用 `export -f` 导出，`PATH` 也前置了 `wrappers/`，所以 dpkg 包脚本、make、安装脚本里的 rm 都走了包装器。
2. 包装器、`hub_delete_file`、回收站都 `resolve()` 操作数，删软链接时挪走的是目标。

修法：
- `rm()` 只定义在 hub_shell 最外层 shell 里，不导出，不改 `PATH`。子进程（脚本、dpkg/apt、make、`xargs rm`、`find -exec rm`、`sudo rm`）和 `/bin/rm` 都是真删。回收站只兜 agent 手敲的 `rm`。
- 删除一律用「父目录 resolve、最后一级不跟随」的路径（`trash.lexical_path`）：软链接只移走链接，断链也能删，`restore` 放回的也是链接。受保护判断对删除同样按链接本身算：指向 `data/` 的软链接可以删，`data/` 里的东西仍不行。写文件照旧跟随软链接。
- 跨设备 `_move` 遇到软链接时重建链接，不复制目标。

### 12.2 写文件原地改

`hub_write_file` / `hub_patch_file` 以前把原文件**挪**进回收站再新建文件：inode 变了（单文件 bind mount 的容器看不到，cliproxy 的 `config.yaml` 就是这种），属主和权限也变回默认（600 会变 644）。现在先复制进回收站，再原地重写。

### 12.3 不守规范的客户端

Operit 收到会话 404 不重新 initialize，一直带旧会话 ID，2.1.1 下只能新开对话。现在每个旧 ID 只回一次 404；同一个 ID 再来就放行，并在第一个工具结果末尾加一行提示（重连可拿到新工具）。守规范的客户端第一次 404 就换了会话，不受影响。记录只在内存里，上限 1000 个，满了清空。

### 12.4 提前清空回收站

`python3 -m sag purge-trash` 只给 root 在服务器上用，**不做成 MCP 工具**，agent 不能自己清掉安全网。按 `--id`（可重复）、`--deleted-by`、`--since`、`--until`、`--prefix` 过滤，至少给一个条件；默认只列出，加 `--yes` 才真删，真删时写一条 `trash_purge` 审计（agent `root:cli`，记下 id 和原路径）。

## 13. 2.1.3：token 脱敏收紧

原规则 `sag_[A-Za-z0-9_]+` 会把 `/tmp/sag_patches`、`sag_latest.bundle` 这类路径也打成 `***TOKEN***`，查审计时看不出删的是什么。SAG token 的格式固定为 `sag_<agent_id 把 : 换成 _>_<48 位 hex>`（`auth.issue_agent_token`，历史上只有这一种），所以规则改为必须以 16 位以上 hex 结尾：`sag_[A-Za-z0-9_.-]*?_[0-9a-f]{16,}`。截断到只剩前 16 位 hex 的 token 仍会打码。已经入库的审计记录是写入时脱敏的，改不回来。

## 14. 发版前备份（只留最新一份）

发版前用 root 在服务器上执行：`cd /opt/server-agents-gateway && sudo python3 -m sag backup-db --label <被替换的版本>`。它会用 SQLite 在线备份，生成 `data/gateway.db.bak-<label>-<时间>`（权限 600），然后删掉更早的 `gateway.db.bak-*`，只留最新的 `GATEWAY_DB_BACKUP_KEEP` 份（默认 1，也可以用 `--keep` 临时指定）。每次执行都会写一条 `db_backup` 审计（agent 是 `root:cli`），记录删掉了哪些文件。这只是一个命令行工具，不影响正在运行的服务，所以更新它不需要重启网关。
